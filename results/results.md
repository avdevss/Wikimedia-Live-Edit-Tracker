# Results

Raw data behind every number in the README. Every figure here traces to a
committed CSV or a command anyone can re-run — nothing here is estimated.

where `label` starts with `after-` (post-optimization runs only, across all

**Method:** each sample is `now - lb:latest_ingest_ts` at the instant the

- n = 122 samples
- p50 = 785ms
- p95 = 988ms
- p99 = 1068ms

## 2. Source-to-ingest lag (Wikimedia's own timestamp → our ingest_ts)

**Indicative only** — mixes in Wikimedia's own propagation delay and any
clock skew on this machine, and their timestamp is only second-granular.
Kept fully separate from pipeline latency (different measurement,
different meaning) per section 6.2.

**Source:** `src/producer/index.ts`'s own histograms, console-dumped every
500 events. Requires a live producer run — not currently written to a CSV,
since it's a live per-event measurement, not a load-test artifact.

**Methodology note, and why there are two histograms, not one.** The
first version of this measurement waited for the sample count to grow
large enough that a post-reconnect burst of high-lag samples would be
"diluted" out of the rolling 10,000-slot ring buffer, then reported
whatever the histogram showed at that point as "settled." That's not
actually proof of exclusion — depending on exactly how many samples the
burst spanned relative to how far the buffer had rotated, some
backlog-contaminated samples could still have been sitting in the buffer
alongside genuine steady-state ones, silently pulling the reported
percentiles up without saying so. Fixed properly: `src/producer/index.ts`
now tracks two separate histograms, `sourceToIngestLagAll` (everything)
and `sourceToIngestLagSteady` (explicitly excludes the first 2,000 events
after every connect/reconnect), logged side by side every 500 events. The
exclusion is structural — steady-state samples are never mixed with
backlog samples in the first place — not inferred from waiting.

**Readings** (from a run with a short gap before reconnecting, so the two
histograms diverge only mildly here — see below for a case where they
diverge sharply):

| | n | p50 | p95 | p99 | p999 |
|---|---|---|---|---|---|
| ALL (includes backlog) | 4,500 | 2007ms | 5102ms | 9723ms | 30407ms |
| STEADY-STATE (excludes backlog) | ~2,500 | 2110ms | 5107ms | 10503ms | 33116ms |

**The split matters a lot more after a longer outage.** An earlier
measurement, taken shortly after the producer resumed from a longer
disconnection gap, showed `ALL` p50 above 20,000ms and climbing toward
30,000+ at p95 during the first ~2,000 events — an artifact of
`Last-Event-ID` resume (confirmed working, plan section 16) delivering a
larger backlog of older buffered events to catch up on, each carrying a
large source-to-ingest gap by construction. That reading was discarded
rather than reported, once the cause was understood — it measured
"propagation delay plus resume catch-up time," not steady-state lag. The
`STEADY-STATE` figures above are what's quoted in the README.

## 3. Aggregator memory under load

**Source:** `results/bench.csv`, `rss_bytes` column (all 8 labels).
**Method:** the aggregator writes its own `process.memoryUsage().rss` to
Redis once per second (`lb:aggregator_rss_bytes`); `bench.ts` reads it
alongside eps/lag/latency on the same cadence.

| Label | Min (MB) | Max (MB) | Growth within the 30s run (MB) |
|---|---|---|---|
| before-1x | 119.6 | 120.1 | 0.5 |
| before-10x | 120.7 | 121.6 | 1.0 |
| before-50x | 122.2 | 125.3 | 3.1 |
| before-100x | 111.9 | 125.7 | 13.8 |
| after-1x | 125.7 | 126.9 | 1.3 |
| after-10x | 125.4 | 125.7 | 0.3 |
| after-50x | 125.6 | 126.8 | 1.2 |
| after-100x | 126.3 | 126.7 | 0.5 |

Memory stayed bounded throughout — never exceeded ~127MB RSS at any tested
load level, before or after optimization, with no sign of unbounded growth
under sustained 100x load. `before-100x` shows the largest single-run
growth (13.8MB) and also the lowest minimum (111.9MB) of any row, both
consistent with a GC cycle happening partway through that particular run
rather than a leak.

## 4. Throughput and consumer lag under load

**Source:** `results/bench.csv`, full file (246 rows: 8 labels ×
~31 rows each — `before-{1,10,50,100}x` and `after-{1,10,50,100}x`).

**Method:** for each multiplier, `tools/replay.ts` ran against the real
capture file (`data/capture-2026-08-19.jsonl`) while `tools/bench.ts`
sampled `eps` (Kafka topic high-watermark growth rate) and `consumer_lag`
(high watermark minus the aggregator consumer group's committed offset)
once per second for 30 seconds. "Before" used the original unbatched,
sequential-produce `replay.ts` and the aggregator's original 4-separate-
round-trip Redis seal. "After" used the batched `replay.ts` (accumulates
and flushes as one send when the next event needs a real pacing gap) and
the aggregator's single-pipeline Redis seal.

| Multiplier | Before mean/max eps | After mean/max eps | Change | Consumer lag (both) |
|---|---|---|---|---|
| 1x | 51.1 / 87.5 | 41.8 / 108.6 | **-18% (regression)** | 0-1, transient |
| 10x | 71.9 / 308.5 | 262.0 / 391.4 | +264% | 0-2, transient |
| 50x | 380.5 / 722.1 | 543.6 / 742.6 | +43% | 0-2, transient |
| 100x | 540.8 / 722.1 | 582.8 / 718.1 | +8% | 0-4, transient |

Lag never sustained or built up at any tested multiplier, before or after
— every non-zero reading returned to 0 within one or two 1-second samples.
The bottleneck throughout was `replay.ts`'s own achievable produce rate,
never the aggregator's consume rate.

**1x regression, explained:** batching only pays off when enough volume
queues up between pacing sleeps to flush together. At 1x (real-time rate),
inter-event gaps are usually large enough that at most one event is ever
waiting — batching adds a small coordination cost (checking/flushing an
almost-always-single-item buffer) with no volume to amortize it against.
This is the expected shape of the tradeoff, not a bug: batching is a
throughput optimization for volume, and 1x deliberately has none to give.

**A real bug found and fixed during this measurement:** the first "after"
attempt at 10x showed `eps` drop to 0.0 and stay there for 24+ seconds
while `pipeline_latency_ms_sample` climbed steadily to 24,346ms. Root
cause: the capture file has a genuine ~5m12s gap between lines 1776 and
1777 (`2026-08-19T08:34:26.236Z` → `2026-08-19T08:39:38.807Z`), from one
of our own producer restarts during earlier testing — not a Wikipedia
quiet period. `replay.ts` faithfully honored that gap, compressed by the
rate, which stalled the load test. Fixed by capping any single inter-event
sleep at 2000ms (`MAX_GAP_MS` in `tools/replay.ts`) — a deliberate,
stated tradeoff of timing fidelity for reliable load-test throughput, see
the README's Limitations section, not just this bug narrative. The run
was then redone cleanly (the table above is the redone, clean data).

Plot: `results/lag-under-load.png`.

## 5. Sketch accuracy and memory

**Sources:**
- `results/sketch-accuracy.csv` — 32 rows: 4 multipliers (25x/50x/75x/100x) ×
  4 memory budgets (xsmall/small/medium/large) × 2 structures (Count-Min
  Sketch, Space-Saving). 100x holds 1,050,000 events — genuinely over a
  million, matching section 6.1's stated bar for a meaningful comparison.
- Exact-counting baseline measured separately, as its own isolated process
  per sample size (`tools/measure-exact-memory.ts`, requires
  `NODE_OPTIONS=--expose-gc`).

**Method:** all multipliers' samples are real captured Wikipedia edit
events (`data/capture-2026-08-19.jsonl`), keyed by editor username. Ground
truth (exact top-20, exact counts) computed via a plain
`Map<string, number>` over the same sample. Each sketch is fed the
identical sequence of events; accuracy is measured against the exact
top-20 (overlap count, mean absolute rank error, mean relative count
error). Cardinality is the true number of distinct editors in that sample.

**Exact-counting baseline, corrected.** The first attempt at this
measurement pre-loaded all sample strings into an array before taking the
"before" heap snapshot. Since `Map.set(key, ...)` stores a reference, not
a copy, every key string was already allocated before the measurement
window even started — the reported delta only ever captured the Map's own
bookkeeping overhead, never the actual string content, and returned a
physically-implausible ~30 bytes/entry. Fixed by streaming the file
directly into the Map one line at a time, with the "before" snapshot taken
before any file reading begins — so each key string's allocation genuinely
happens inside the measured window, and only what the Map retains survives
the closing `gc()`.

At the 50x sample (525,000 events, 15,404 distinct editors):
- First corrected run: 1,408,888 bytes
- Second corrected run: 1,397,912 bytes (0.8% apart — consistent, not a
  discrepancy worth chasing further)
- **Baseline used for the headline number: 1,403,400 bytes** (average of
  the two), ≈91 bytes/distinct key — a plausible figure for a JS Map
  holding string keys (V8 per-entry overhead plus real string storage),
  unlike the original ~30 bytes/key result.

**Selected comparison points** (50x, 15,404 distinct editors):

| Structure | Budget | Bytes | Top-20 overlap | Mean count error | Reduction vs exact |
|---|---|---|---|---|---|
| Count-Min Sketch | large | 65,536 | 20/20 | 0.09% | 21.4x |
| Space-Saving | large | 22,444 | 20/20 | 0.06% | 62.5x |
| Space-Saving | medium | 5,638 | 19/20 | 0.61% | 248.9x |
| Count-Min Sketch | xsmall | 4,096 | 18/20 | 6.03% | 342.6x |

Space-Saving is consistently more memory-efficient than CMS at equal byte
counts across the full range tested (see plot) — CMS's own "xsmall" tier
looked competitive against Space-Saving's "xsmall" tier in isolation, but
that comparison used mismatched byte counts (4,096 vs 1,298 bytes); at
truly equal memory, Space-Saving wins throughout.

Full data: `results/sketch-accuracy.csv`. Plot: `results/sketch-accuracy.png`.

## Reproducing all of this

```bash
# 1. Load test + before/after bench data (results/bench.csv)
npx tsx tools/replay.ts --file data/capture-<date>.jsonl --rate <N>   # separate terminal
npx tsx tools/bench.ts --out results/bench.csv --duration 30 --label "<label>"

# 2. Source-to-ingest lag (console only). Watch for the STEADY-STATE line
#    specifically, not ALL — it excludes the first 2000 events after
#    connect by construction, so it's valid as soon as it has samples
#    (roughly 4000-4500 total events in), no waiting-and-hoping required.
npm run producer

# 3. Sketch accuracy (results/sketch-accuracy.csv)
npx tsx tools/sketch-accuracy.ts --file data/capture-<date>.jsonl

# 4. Exact-counting memory baseline
NODE_OPTIONS=--expose-gc npx tsx tools/measure-exact-memory.ts --file data/capture-<date>.jsonl --sample-size 525000

# 5. Plots
python3 -m pip install matplotlib   # one-time
python3 tools/plot.py
```
